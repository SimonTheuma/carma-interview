# carma-benchmark
 
A benchmark is a small, repeatable, runnable experiment that answers one question about the latest changes: **is the data still complete, and is it still fast enough?** It is not the full test plan (that is carma-backend-testing) and not production load. It is the quick check a developer or agent can run after a change and trust.
 
Read `references/carma-context.md` first for the principles, constraints and spec conventions.
 
This skill runs outside the main carma flow. It can be used at any time on the current state of the code, with or without specs.
 
## Inputs
 
1. **The change.** Find the latest changes (`git diff`, `git log`, or the files the user names). Read the changed code and what it calls.
2. **The specs, if any.** `.specs/architect/` (hot paths HP-n, failure points FP-n, throughput budget), `.specs/data/dba/` (schema, write path), `.specs/testing/backend/` (load profiles and thresholds, so numbers match), `.specs/telemetry/` (counters the benchmark can read), `.specs/devops/` (the Compose stack the benchmark can run against), and the plan in `.specs/plan/` (what the change was meant to deliver).
3. **Existing benchmarks** in `.benchmarks/`. Extend or update them instead of creating near-duplicates.
## Workflow
 
### 1. Decide what to measure
 
From the change, choose the question. Usually one of:
 
- **Completeness** (preferred when in doubt, because a missed mention is the worst failure, P3): every input is accounted for at the end, `received = stored + rejected + quarantined + dead-lettered + duplicate`, text fidelity by hash, planted mentions are all found, nothing stuck "in progress".
- **Performance**: sustained throughput against the 800 articles/sec target, latency percentiles of the changed path, resource cost per article, and freshness from `published_at` to searchable where the path covers it.
- **Both** at once, which is the common case: run at a target rate and verify completeness at the end.
Link each measurement to a failure point or hot path in the specs when they exist, so the benchmark covers what the architect said to watch.
 
### 2. Check feasibility, and ask when it is not obvious
 
Not every change can be benchmarked cheaply. Before writing anything, work out which of these applies:
 
- The change can run in-process with no external services (pure functions, parsing, normalisation, scoring math): easy, benchmark the function directly.
- It needs PostgreSQL: use the Compose stack or a disposable database, with the connection from environment variables. Ask which instance to use and warn that a shared or production database must never be the target.
- It needs an external dependency (an LLM, a source feed): use a fake or stub with controllable latency and failures, and say that the result then measures our code, not the dependency.
- It is a UI, a one-off script, a config change, or has no measurable behaviour: say so and recommend not writing a benchmark, or a different kind of check.
When the approach, the data or a caveat is unclear, **prompt the user before writing code**, using the protocol in the context file (grouped questions, recommended option first, trade-offs in a line). Typical questions:
 
- What to benchmark: completeness, performance or both, and which path.
- The approach: in-process micro benchmark, against a local database, against the Compose stack, or end to end through the real entry point.
- The data: generated by the bundled generator (default), a sample the user supplies (anonymised), or a captured file; the size and language mix.
- Thresholds: use the agreed 15-minute and 800/s numbers where they apply; ask for the rest or propose values and label them `proposed`.
- Caveats the user accepts: stubbed dependencies, small data volume, hardware not production-like, short duration.
If nobody can answer (unattended run), choose the cheapest approach that answers the question, label each assumption `UNCONFIRMED` in the benchmark's README and in the console output header.
 
### 3. Design the benchmark
 
Write down, in the benchmark's README, before the code:
 
- The question, the change under test and the linked FP/HP entries.
- The approach and what is real versus stubbed.
- The load shape: rate, duration, warm-up, concurrency, seed, language mix, planted mention rate, duplicate and late-arrival rate. Default to a short run (10 to 60 seconds) that gives stable numbers; offer a longer soak as an option rather than the default.
- The metrics reported and each check with its threshold, labelled **agreed** (from the client or an approved spec) or **proposed**.
- How completeness is verified: against the system of record (query the database or ledger), never against the benchmark's own bookkeeping alone.
- Setup, run and clean-up steps, and that the benchmark leaves the target database as it found it (its own schema or marked rows that it removes).
### 4. Write it
 
Place everything in `.benchmarks/<feature-slug>/`:
 
- `bench-lib.mjs`: copy from `assets/bench-lib.mjs` (dependency-free, Node 18+). It provides seeded article generation (English, Arabic, Chinese, planted brand mentions, duplicates), a rate-paced load runner with bounded concurrency, latency percentiles, error aggregation, a `Report` with PASS and FAIL checks, a conservation helper and a `main` wrapper. Do not rewrite these; extend through the benchmark script. Improve the copy in the benchmark folder if it is genuinely missing something.
- `bench.mjs`: start from `assets/bench.template.mjs`. Import the code under test, drive the load, verify completeness, and set thresholds.
- `README.md`: the design from step 3 and how to run it.
- `.gitignore` with `results/`, so outputs are not committed.
- Dependencies: use Node's standard library. If the benchmark needs a database driver, use the one the project already depends on, and say so in the README. Do not add heavy tooling for a quick check.
Requirements for every benchmark:
 
- **Runs with `node .benchmarks/<feature>/bench.mjs [--rate N --duration S --seed N ...]`**, with defaults that work without arguments.
- **Clear errors.** Errors encountered while running are aggregated and printed with counts, a sample context and a short stack, and never swallowed. A benchmark that cannot run (missing environment variable, database unreachable) says what is missing and exits with code 2, distinct from a measured failure.
- **Clear verdict.** The console shows the metrics, a checks table with PASS or FAIL per check and each threshold's origin, and a final `RESULT: PASS` or `RESULT: FAIL` line. Exit code 0 for pass, 1 for fail, 2 for could not run.
- **Reproducible.** A seed, and the environment (Node version, hardware summary, database settings if relevant) printed in the header. Performance numbers without their environment are not comparable.
- **Honest.** Warm-up excluded from the measured window; the achieved rate reported next to the target (if the generator or the harness cannot keep up, that is shown, not hidden); percentiles rather than averages; no threshold chosen so that today's result happens to pass.
- **Safe.** No secrets in the files. Connection details come from environment variables. Refuses to run against a database whose name or host looks like production unless explicitly overridden. Never prints credentials.
- **Cheap to read.** Keep `bench.mjs` short and plain; the harness carries the machinery.
### 5. Run it and report
 
Run the benchmark at least once if the environment allows, and show the real console output. If it cannot be run here (no database), say so, state what remains to be verified, and do not invent numbers. If it fails, report what failed and whether it points to the change, the benchmark or the environment. When a result looks surprising, run again with a different seed before concluding.
 
### 6. Feed back into design
 
Benchmarking often reveals design issues. State them plainly, and raise those that need a decision:
 
- Code that is hard to benchmark is hard to test and operate. Note where a seam is missing: a function that cannot be called without the whole service, a hidden dependency on the system clock or random source, no way to read how many items were processed.
- Missing counters or ledger states needed to verify completeness (route to carma-telemetry and carma-dba).
- Hot paths that miss budget (route to carma-architect, and to carma-review for readability of that path).
- A needed environment or fixture (route to carma-devops, for a Compose `bench` profile).
- A threshold nobody has agreed (route to the user).
Do not change the architecture silently. Write the findings in the README under "Design implications" and in the reply.
 
## Output
 
In the reply: what was benchmarked and why, the approach and caveats, the run command, the real console result or what prevented a run, and the design implications. The artefacts are the files under `.benchmarks/<feature-slug>/`.
 
## Persisting the work (when run inside a codebase)
 
The benchmark itself lives in `.benchmarks/<feature-slug>/` as above. If the work leads to a binding decision (for example an agreed threshold), suggest recording it as an ADR through carma-architect. If you are not in a codebase, deliver the files in the conversation and offer to save them.
